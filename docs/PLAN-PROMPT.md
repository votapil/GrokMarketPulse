# Мета-промпт: разбить ТЗ на задачи для двух разработчиков

Как использовать: открыть Claude Code в plan mode (Shift+Tab дважды), вставить текст ниже,
а сразу под ним — полное ТЗ. Получить `PLAN.md`, закоммитить, напарник делает `git pull`.

---

Ты — тимлид на однодневном хакатоне. Нужно разбить ТЗ (ниже) на план параллельной работы
двух разработчиков, каждый со своим Claude Code на своей машине, общий репозиторий на GitHub.

## Сначала прочитай
- `AGENTS.md` — что за продукт и как устроен проект
- `docs/STACK.md` — доступные API спонсоров, ключи, живые ограничения
- `.claude/settings.json` — какие плагины есть у обоих участников
- реальное состояние кода (`git log --oneline -20`, дерево файлов) — план должен начинаться
  с того, что уже есть, а не с нуля

## Жёсткие ограничения на декомпозицию

1. **Дедлайн: <ВПИШИ ВРЕМЯ СДАЧИ>.** Обратный отсчёт от демо, а не вперёд от задачи.
   Заложи 25% времени на интеграцию и репетицию демо. Всё, что не влезает — в раздел
   «Не делаем» с одной строкой почему.

2. **Задача = один коммит = 30–45 минут.** Если больше — дели. Каждая задача — вертикальный
   срез: после неё приложение запускается и что-то показывает. Красный main запрещён.

3. **Непересекающееся владение файлами — главное правило.** Две задачи, идущие параллельно,
   не имеют права трогать один файл. Для каждой задачи явно перечисли:
   - `Владеет:` файлы, которые задача создаёт/меняет (только она)
   - `Читает:` файлы, на которые опирается, но не правит
   Общие файлы (`convex/schema.ts`, роутер, `package.json`, общие типы, `tailwind.config`)
   правятся ТОЛЬКО в одиночных задачах — точках синхронизации, где вторая дорожка стоит.
   Таких точек должно быть минимум: в идеале одна в начале.

4. **Контракты замораживаются первой задачей.** Задача T-01 — единственная общая: схема
   Convex, TypeScript-типы, сигнатуры query/mutation/action, формы ответов внешних API,
   моковые данные. После неё обе дорожки пишут код против зафиксированных типов и не
   встречаются в файлах. Если контракт приходится менять позже — это отдельная
   sync-задача, а не правка по ходу.

5. **Моки вместо ожидания.** Фронт не ждёт бэкенд: T-01 отдаёт фикстуры в
   `src/lib/fixtures.ts`, UI пишется против них, подключение живых данных — отдельная задача.

## UX — главный критерий, не побочный

Перед списком задач опиши **демо-сценарий**: ровно то, что человек делает на сцене за
90 секунд, по шагам, с экранами.

Правила, которым план обязан подчиняться:
- **Не больше 3 экранов.** На каждом — одно главное действие, одна заметная кнопка.
- **Нулевой онбординг:** пользователь видит результат до любого ввода. Экран не должен
  быть пустым при первом открытии — предзаполненные данные/пример.
- **Ни одного обязательного поля ввода на пути демо,** если без него можно обойтись.
- **Запрещено без явного требования ТЗ:** авторизация, регистрация, настройки, админка,
  профиль, онбординг-туры, модалки подтверждения, многошаговые формы, боковое меню.
- **Состояния обязательны:** loading / empty / error для каждого экрана — это часть DoD
  задачи, а не отдельная задача «потом».
- LLM-ответ ждём больше секунды → скелетон или стриминг, не спиннер в пустоте.
- Если задача не двигает демо-сценарий — она не входит в план.

### 3. Замороженные контракты

### 6. Git-протокол (вписать в PLAN.md дословно)

Работаем в `main` короткими коммитами, без PR — на день это быстрее и безопаснее,
чем ветки, ПРИ условии непересекающегося владения файлами.

```bash
# перед стартом задачи
git pull --rebase origin main

# после задачи — сначала проверка, потом коммит
npm run build && git add -A && git commit -m "T-07: ..." 
git pull --rebase origin main && git push origin main
```

- Один коммит = одна задача, в сообщении ID задачи.
- Не начинать задачу, не сделав pull.
- Конфликт при rebase = нарушение владения файлами: остановиться, написать напарнику,
  не разрешать конфликт «на глаз».
- `.env.local` и ключи не коммитим никогда; новые переменные — только в `.env.local.example`.
- Отметку о выполнении ставить в `PLAN.md` тем же коммитом (галочка в таблице).

### 7. Приёмка «как жюри» — что делает тот, кто принял `git pull`

После каждого pull чужой работы — 3 минуты, не больше:

```bash
git pull --rebase origin main
git log --oneline -5
/ecc:code-review           # ревью входящего диффа
npm run build && npm run dev   # руками пройти демо-сценарий целиком
```

Рубрика жюри (та же, по которой судят проект — отметить да/нет):
- [ ] **Работает вживую.** Демо-сценарий проходится целиком, без перезапуска и без консоли.
- [ ] **Просто.** Путь до результата — не больше 3 кликов, ни одного объяснения вслух.
- [ ] **Видно ценность** за первые 10 секунд на экране.
- [ ] **Спонсорские API реально задействованы** и это видно в интерфейсе.
- [ ] **Не сломано ранее работавшее** (регрессия по предыдущим шагам сценария).
- [ ] Секретов в диффе нет, сборка зелёная.

Любое «нет» → чинит автор задачи, не принимающий. Принимающий пишет одну строку в
`PLAN.md`: `T-07 принято` или `T-07 возврат: <что именно не так>`.

### 8. Контрольные точки по времени
Три отсечки с формулировкой «что показываем, если время кончится прямо сейчас».
На каждой — состояние, которое уже можно показать жюри.
